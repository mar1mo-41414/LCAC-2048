# ARCHITECTURE

Auto2048 v3 の仕組み。対象は **2048 4.0.8** (`com.ketchapp.2048`) の通常ゲーム、4×4 盤面です。
利用者向けの症状別の対処は [TROUBLESHOOTING.md](TROUBLESHOOTING.md)、開発の経緯は [../HISTORY.md](../HISTORY.md) にあります。

## 方針

- UnityFramework の IL2CPP API を `dlsym` で名前解決します。JIT やインラインフック、ゲームバイナリへの書き換えは行いません。
- ゲーム内部の取得と入力はメインスレッド上で行い、探索だけをバックグラウンドで実行します。
- 解析したゲームの内部クラス・メソッド名に依存します。バージョン変更後の互換性は保証しません。
- UI と IL2CPP のアプローチは [LCAC-A](https://github.com/mar1mo-41414/LCAC-A) を参考にしています。ゲーム本体やその抽出データは含めません。

## 構成

| ファイル | 役割 |
| --- | --- |
| `Sources/Controller.m` | `AUTO` ボタン (タップ / 長押し)、`CADisplayLink` のループ、速度設定の保存、状態表示 |
| `Sources/Engine.m` | IL2CPP のシンボル解決、ゲームオブジェクトの取得、盤面の読み取りと `HandleSwipe` の呼び出し |
| `Sources/Solver.c` | 移動・合体のシミュレーションと expectimax 探索 (ゲーム側に依存しない純 C) |
| `tests/` | ホスト側で動くソルバーのテストと簡易シミュレーション |

## ゲーム側の構造

| 対象 | 用途 |
| --- | --- |
| `Game2048.GameManager` | `UnityEngine.Object.FindFirstObjectByType(Type)` で取得。`_currentGame` と `HandleSwipe(Vector2Int)` を利用 |
| `Game2048.GameModes.RegularGame` | 通常ゲームかどうかと `GameActive` を確認 |
| `Game2048.GameModes.GameMode` | `get_Grid()` で盤面を取得 |
| `Grid` | `get_Size()` と `GetCellValue(Vector2Int)` で 4×4 の各マスを読む |
| `GridViewManager` | 表示中の `_grid` が取得した盤面と一致し、`IsAnyTileMoving()` が false であることを確認 |

`il2cpp_runtime_invoke` でゲームのメソッドを呼び、例外を確認します。フィールドも IL2CPP API を通じて名前で取得し、
盤面そのものを直接書き換えず、ゲームの `HandleSwipe` に方向を渡します。

### `FindFirstObjectByType` の落とし穴

`FindFirstObjectByType` には引数 1 個のジェネリック版 `<T>(FindObjectsInactive)` もあります。
名前と引数数だけで引くとそちらを掴むため、`il2cpp_class_get_methods` を回して
**非ジェネリック (引数が `System.Type`) の版**を選びます。
v2 ではこれにより、実機で管理オブジェクト取得時に出た `F_EXC` の有力な原因を修正しました。

## 探索

`Sources/Solver.c` は、各方向の移動と合体を盤面のコピー上で計算し、expectimax 型探索を行います。
**4 手先から始めて、1 手あたりの計算量 (ノード数、上限 20 万) が収まる範囲で 1 手ずつ深くします (最大 6 手先)**。
終盤は分岐が小さいので自然に深くなり、序盤は浅いままですみます。途中で合法手がない場合はそこで打ち切ります。
空きマスが 4 個以下になったら、**その盤面だけ上限を 4 倍 (80 万) に広げ、最大 8 手先まで**読みます
(`ENDGAME_EMPTY` / `ENDGAME_BUDGET_MULT` / `ENDGAME_MAX_DEPTH`)。終盤は分岐が小さく、
しかも 1 手の誤りがそのままゲームオーバーになる場面なので、時間をかけずに精度だけを上げられます。
ノード数は決定的なので、同じ盤面からは常に同じ手を返します (テストで確認しています)。

探索のパラメータ (`DEPTH` / `MAX_DEPTH` / `NODE_BUDGET` / `SAMPLE_CELLS` / `ENDGAME_*` / `MERGE_*`) と
評価の重み (`W_*`) は `-D` で差し替えられるようにしてあります (既定値は出荷設定)。ベンチは次のとおりです。

```
make test
cc -O2 -I Sources tests/simulate.c Sources/Solver.c -lm -o build/simulate   # games maxmoves spawn
./build/simulate 4 4000 4            # 4 ゲーム、4,000 手まで、出現は 4 固定
# 例: 終盤の深掘りを止めて比べる
cc -O2 -I Sources -DENDGAME_BUDGET_MULT=1 tests/simulate.c Sources/Solver.c -lm -o /tmp/sim_flat
```

`tests/simulate.c` はスコアと最大タイルも出力します。深さ・サンプル数・重みを変えて比べるときは、
`-DDEPTH=3 -DMAX_DEPTH=3 -DNODE_BUDGET=25000 -DSAMPLE_CELLS=3` のような軽い設定で 24 シードを回すと
1 分ほどで傾向が分かります (細かい差は出荷設定で取り直してください)。

- 新しいタイルは 2 が 90%、4 が 10% で出ると仮定します。ゲーム側での確率は確認していません。
  出現タイルを 4 に固定できたとき (下記) は、4 だけが出る前提で読みます。分岐が半分になるぶん、
  同じ計算量で 1〜2 手深く読めます。
- 空きマスが 4 個以下なら全位置、5 個以上なら最大 4 位置 (`SAMPLE_CELLS`) を選んで確率を近似します。選択位置は盤面ハッシュにより回転させます。
- このため、読んでいる深さの全出現パターンを厳密に網羅するわけではありません。盤面・深さ・ノード種別を使う探索内キャッシュで再計算も抑えます。
- 盤面評価は空きマス、数字の単調性、隣接する数字の差、合体候補、最大値の角配置、角からの蛇行順を考慮します。
  蛇行順は回転・反転した 8 向きから最良を選び、特定の角には固定しません
  (角に固定すると 1024 同士を寄せるための組み替えができず、実測で悪化しました。HISTORY.md 参照)。
- 空きマスは数だけでなく**形**も見ます。隣の空きマスとつながっている空きマスには +200 を足します。
  孤立した 1 マスの穴は盤面を組み替える余裕にならないため、安く見積もります。
- 合体候補はタイルの大きさで重み付けします。1024 同士が隣り合っていることを、2 同士が隣り合っていることより重視します。
- ただし、この「隣り合ったペア」の評価だけでは、2048 + 2048 を 4096 にするより
  ペアのまま残すほうが高得点になり、4 手先の探索では差を読み切れません。
  そこで**最大タイルの 2 枚を合体させる手に固定ボーナス (1,500) を足し**、合体できるペアは必ず合体させます。
  合体後の盤面が最も良い向き (角に残る向き) は今まで通り探索で選びます。
- 明示的な「2048 になったら停止」はなく、通常ゲームを続行するための方策です。2048 達成やゲームオーバー回避は保証しません。

### 出現タイルを 4 に固定する (実験的)

実機では、新しいタイルを 2 ではなく 4 に固定できると盤面が早く育ちます。
`Sources/Engine.m` は起動後に一度だけ次を試します。

やることは 2 段構えです。どちらも「確認できなければ何もしない」ようにしてあります。

1. **確率フィールドを探す**: `GameManager` と `Grid` の `float` フィールドを走査し、名前が `four` を
   含むものがあれば 1.0 にします (`il2cpp_field_set_value`)。見つかった場合は
   ソルバーにも「4 だけが出る」と伝えます (`solver_set_spawn_value(4)`)。
2. **見つからない場合は出たタイルを書き換える**: `Grid` のセッター (`SetCellValue` など) を探し、
   **実際に書いて読み直して一致したときだけ**使います。以後、盤面を読むたびに 2 を 4 に
   書き換えます (`writeCell`)。書き換えた値は必ず読み直してから使うので、
   推測が外れてもソルバーに嘘の盤面を渡すことはありません。

安全装置:

- 書き換えが効かない・2 が戻ってくる (1 手で 2 が 3 個以上見える) 場合は、その場で止めて
  2 / 4 のモードに戻します。ゲームを壊さないための自己修正です。
- フィールドもセッターも無い場合は、名前だけログに出して従来通り 2/4 で動きます。
  ログは `[2048-auto]` で検索してください ([docs/TROUBLESHOOTING.md](TROUBLESHOOTING.md))。
- このゲームのビルドはログ上でメソッド名を伏せる (`<private>`) ため、名前を確認したいときは
  **7bit で詰めた数値**として出す必要があります (`<private>` は os_log が文字列だけを伏せるため)。

### 調べて分かった `Grid` の API (試作2 のログから)

| メソッド | 引数 | 役割 |
| --- | --- | --- |
| `get_Cells` | 0 | タイルの配列 |
| `GetCellValue(Vec2)` | 1 | セルの値 |
| `SetCellValue(Vec2, int)` | 2 | セルの値を書く (本命の書き換え先) |
| `Move(Vec2)` | 1 | 1 手進める |
| `AddRandomTileInFreeCell()` | 0 | タイルの出現 |
| `AddTileInFreeCell(...)` | 1 | 指定した場所にタイルを置く |
| `GetRandomAvailableCell()` | 0 | 空きマスの抽選 |
| `SetTileAdder(...)` | 1 | タイル生成のコールバック |
| `UpgradeAllTiles()` | 0 | 全タイルを 1 段上げる (チート) |

`Tile` という名前のクラスは見つかりませんでした (タイルは `Cells` の中身としてのみ扱えます)。

## スレッドと安全確認

1. `CADisplayLink` のメインスレッドで対象モード・ゲーム状態・盤面・表示中の盤面・アニメーションを確認し、16 マスを読み取ります。
2. コピーした数値だけをバックグラウンドのソルバーに渡します。IL2CPP オブジェクトにバックグラウンドからアクセスしません。
3. メインスレッドに戻ったら、AUTO が ON のままでアプリがアクティブなことを確認します。OFF やバックグラウンド移行時は探索結果を無効化します。
4. ゲーム・盤面インスタンス、ゲーム状態、アニメーション、16 マスを再確認し、変化していれば `STALE` 等を表示して操作を行いません。
5. 結果が現在も合法なら `HandleSwipe` を呼びます。ゲームオーバーや達成画面ではゲーム側の状態により `PAUSE` になる場合があります。

無効化は `epoch` のカウンタで行います。`AUTO` の ON / OFF、前面から外れたとき (`UIApplicationWillResignActiveNotification`)、
探索の開始時に `epoch` を進め、戻ってきたときの値が違えば結果を捨てます。

## AUTO ボタンと状態

起動時 OFF。タップで ON/OFF、長押しで速度を切り替えます。速度は保存されますが ON/OFF は保存されません。
操作後の最低待ち時間は x1 = 0.45 秒、x2 = 0.32 秒、x4 = 0.22 秒、**MAX = 待ちなし (0)** です。
MAX では前の 1 手が終わり次第すぐ次の手を考えます。実際の間隔は探索時間とゲームのタイル
アニメーション待ちだけで決まります。

状態表示は `Sources/Controller.m` の `status`、ゲーム側の状態は `Sources/Engine.m` が返す文字列です。
表示ごとの意味と対処は [TROUBLESHOOTING.md](TROUBLESHOOTING.md#状態表示の一覧) にまとめています。
`END` / `ERR` / `DATA` / `SIZE` では自動停止します。

ボタンは前面のウィンドウの右下に固定し、ウィンドウが変わったとき (画面遷移・回転) に付け直します。
広告・ポップアップの完全な検出はありません。例外や解決失敗は `NSLog` に出力する箇所がありますが、
専用の Documents ログファイルは作成しません。

## 検証

```bash
make test        # 単体テスト + 10,000 盤面の移動処理比較
make simulate    # 簡易シミュレーション (3 ゲーム × 5,000 手)
```

ホスト側で単体テストと 10,000 盤面の移動処理比較を実施。2 / 4 の出現率を 90 / 10 とする簡易シミュレーション
16 シード × 4,500 手で、4096 到達は 11 回、平均最大タイルは 3,456 でした (1,024 で崩れる例はなし)。
試行回数が限られており、実機での到達率を示すものではありません。
実機では v3 の自走と 2048 達成を 1 回確認しています。

## 未対応・既知の制限

- チャレンジ・対戦モード、4×4 以外の盤面。
- 自動リスタート、広告・ポップアップの自動操作。
- 2048 4.0.8 以外のバージョン (内部クラス名・メソッド名が変わると解決に失敗します)。
- `Engine.m` / `Controller.m` は iOS SDK と実機が必要なため、CI ではビルドもテストもしていません。
